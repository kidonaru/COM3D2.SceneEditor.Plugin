# COM3D2 タイムライン編集

ユーザーが指定したXMLと対象のキーを編集する。回答・コードコメント・エラーメッセージは日本語にする。

## 調査

- [XML仕様](references/xml-spec.md)で階層、型別の値順、互換性と実装の確認先を確認する。ここに記載した仕様は2026-09-07のSceneEditor実装とversion 33の実ファイルに基づく。未知の版や型は、対象XMLと利用中の実装を優先する。
- まず `version`、`FrameRate`、レイヤーの `ClassName` / `SlotNo`、対象登録、対象の全キーフレームを抽出する。数十万行あるXML全体を会話に流さない。context-modeが利用できる場合は解析に使う。アクセス拒否時は権限を迂回せず、許可された読み取り手段に切り替える。
- ソースに `.codegraph/` がある場合、コードの定義・呼び出し調査にはCodeGraphを先に使う。なければ索引作成せず通常の検索を使う。ライブラリの使い方を調べる場合はContext7を使う。
- 「ライト」という呼称だけで `LightTimelineLayer` と決めない。`.menu`のビームライトは通常のモデルであることがある。対象の `Type` と登録先を確認する。

## 編集の要点

1. 原本のバイト列・更新状態を把握し、上書き前に同じフォルダーへ一意な名前のバックアップを作る。書き込み直前に原本が変わっていないことを確認する。作業領域外の書き込みはホストの許可手順に従う。
2. 対象を `ClassName + SlotNo + FrameNo + Transform/Name` で限定する。配列は **Transform直下のValueだけ** を読む。子孫検索ではタンジェントや文字列のValueが混入する。
3. [編集手順](references/edit-recipes.md)に従い、必要な登録とキーを対応させる。大きなXMLは解析用DOMと保存用の限定置換を分けると無関係な整形差分を抑えられる。置換は対象件数を検証し、CRLF・文字コード・BOM・未知の要素を保つ。
4. モデル複製の採番は **接尾辞なし、(2)、(3)、…、(N)**。`(1)`を作らない。登録とキーが互いに一致していても、ゲームが付け直す番号と違えば壊れる。`SlotNo`をモデルの通し番号に使わない。
5. 座標・クォータニオン・Euler角を型ごとの仕様で扱う。既存のスケール、可視性、補間情報、対象外のアニメーションを保持する。静止配置の変更と、全キーに及ぶアニメーション変換を区別する。
6. 保存前後にXML構文、登録とキー、採番、値数、対象外差分を検証する。円周配置なら半径・高さ・角度間隔・重複終点も確認する。エラーを直せない場合は原本への反映を止め、原因を伝える。

## ビームライトの材質同期

ステージレーザーの明るさ・色を光源モデルの `EmissionValue` / `EmissionColor` に同期する場合は、[同期手順](references/beam-material-sync.md)と `scripts/sync_beam_materials.py` を使う。対応するコントローラーと材質名をJSONで指定し、検証してから反映する。色だけを追加する場合は `--channels color` で既存の明るさを維持する。

「仮装狂騒曲 篠澤広」の対応表は `references/beam-sync-kasou.json`。床の(0)(1)(2)(3)とビームライト(11)(15)(8)(18)の対応だけを含む。高所の(4)(5)と残りのモデルへ同期を広げない。他シーンでは実際の登録名と光源位置から対応を決める。

## 材質キー複製の参考スクリプト

登録済みの同一モデル全体へ、指定フレームの材質設定を複製する場合は [scripts/replicate_material_key.py](scripts/replicate_material_key.py) を利用できる。引数・対象形式・保存方法は [使い方](references/material-key-reference.md) を参照する。既定は読み取り専用で、異なる既存設定は上書きしない。

## 読み取り専用の検証

スキルフォルダーを基準に実行する。パスと対象名は実際の依頼に置き換える。

```powershell
python scripts/inspect_timeline.py '対象.xml'
python scripts/inspect_timeline.py '対象.xml' --model '対象.menu' --expect-count 24 --require-frame 0 --show-models
```

`--model` は接尾辞なしの正確なモデル名。`--expect-count` は元を含む合計。`--require-frame` はそのフレームのキーを依頼上必要とする場合だけ指定する。スクリプトはファイルを書き換えず、JSON要約とエラーを返す。採番は実装の `FixGroup` 規則でも照合する。全型・全旧版・ゲーム内のロード成功を保証するツールではない。

ゲームを操作できるMCP等が実際に利用でき、依頼の範囲であれば再読み込み後のモデル名、キー、位置を確認する。未保存のゲーム内編集を勝手に破棄しない。XML検証だけの場合は「ゲーム内確認済み」と言わない。完了時に変更内容、検証結果、バックアップの所在を簡潔に伝える。
