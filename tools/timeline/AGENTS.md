# タイムライン作業の配置と進め方

## 探す順序

1. [README.md](README.md) で目的に合うスクリプトを確認する。
2. ビームの色・明るさ・回転なら、先に [references/beam-material-sync.md](references/beam-material-sync.md) を全文読む。
3. シーン固有の設定は `scenes/<scene-id>/README.md` からたどる。「仮装狂騒曲 篠澤広」は [scenes/kasou-hiro/README.md](scenes/kasou-hiro/README.md)。
4. 現行スクリプトを探すときは `scripts/` と対象シーンの `scripts/` に検索範囲を絞る。`archive/` は過去の経緯を調べる場合だけ読む。

## 配置ルール

| 内容 | 保存先 |
| --- | --- |
| 再利用する変換・検証処理、共通モジュール、テスト | `scripts/` |
| 共通の仕様・操作手順、既存ビーム対応表 | `references/` |
| シーン固有の編集スクリプト | `scenes/<scene-id>/scripts/` |
| シーン固有の設定JSON、編集計画 | `scenes/<scene-id>/plans/` |
| 調査・変更記録 | `scenes/<scene-id>/docs/` |
| 共有・保存する参照画像 | `scenes/<scene-id>/images/` |
| 生成XML、検証結果、一時スクリプトなどの未確定作業 | `work/<scene-id>/<task-id>/`（Git対象外） |
| 置き換え済みツール、撤回した設定、過去の作業一式 | `archive/<task-id>/` |

- 新しいスクリプトを作る前に、同じ目的の既存処理を探して改修できないか確認する。
- 同じ処理を別の `*-work` フォルダーへコピーして開発しない。継続利用するものは `scripts/`、一時的な試作は `work/` に置く。
- 配置変更時はREADME・Markdownリンク・スクリプト内の参照も更新する。撤回済み資料は、現行手順と混同しないよう `archive/README.md` に理由を書く。
- XMLはユーザー指定の場所にある原本を扱う。原本そのものをこのリポジトリへ移動しない。原本のバックアップは編集スキルの手順に従い、原本と同じフォルダーへ作る。

## 正式なソースとインストール済みスキル

変換スクリプトの開発元はこのディレクトリの `scripts/`。Codexの `com3d2-timeline-edit` スキルにある同名ファイルは実行用のコピーとして扱う。スキルの場所はセッションのスキル一覧から取得し、固定ユーザー名を埋め込まない。

- 改修前に実行用コピーとの差分を確認し、新しい変更を古いコピーで上書きしない。
- `sync_beam_materials.py`、`sync_beam_pose.py`、`beam_curves.py` の依存関係を保つ。仕様を変えたら `references/beam-material-sync.md` と関連テストも更新する。
- リポジトリ側とスキル側の対応表には、`emission_max` などの利用者設定の差があり得る。スクリプト更新に便乗して対応表を無断で上書きしない。
- スキル側へ反映する場合はホストの書き込み権限手順を使い、既存ファイルをバックアップしてからコピーし、ハッシュを照合する。旧 `archive/beam-sync-work/install_sync.ps1` は利用しない。

## 改修とXML反映を区別する

「変換スクリプトを改修する」依頼では、生成処理を修正し、既存XMLへの手作業のキー削減で代用しない。ユーザーの依頼範囲にXML反映が含まれる場合に、改修済みスクリプトで検証して反映する。

ビーム同期は対応表に含まれる対象だけを変更する。補間は現行ゲーム実装を確認し、色・数値・クォータニオンを同じ補間と決めつけない。同期元から計算した全整数フレームとの誤差、対象外データ、再実行時の安定性を検証する。

リポジトリルートからの回帰テスト:

```powershell
python -m unittest discover -s tools/timeline/scripts -p 'test_*.py'
```

XML反映前後には原本の更新検知・バックアップ・再読検証を行う。ゲーム内確認を実施していない場合は、その旨を明記する。
